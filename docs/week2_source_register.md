## Campus and user coverage

The current handbook is not KL-only. Its public outline lists Johor Bahru, Kuala Lumpur and Pagoh in the directory and operating-hours sections; viewer page 35 also identifies these locations in borrowing/returning guidance. This confirms multi-campus coverage, not identical rules for every campus.

The handbook also contains separate undergraduate, postgraduate, staff and external-member sections. Availability of those sections does not mean the semester prototype must serve every group. The proposed V1 serves undergraduate students and selected library-service topics; it retains campus applicability as source metadata and clarifies campus only when it affects the answer.

## Observed source-quality issues

1. **Version overlap:** first-edition pages coexist with newer pages and an AY2026/2027 handbook. A page remaining online is not proof that its policy is current.
2. **Policy conflict:** S16 and S09 contain inconsistent fine details. These entries require adjudication against the latest handbook before being used as reference answers. The assistant must not choose a value merely because retrieval ranks it first.
3. **Terminology mismatch:** S08 uses both LESTARI and OCEAN within its renewal instructions. A name-only difference is not treated as a material policy conflict. Use the latest supported service name in the answer and preserve a legacy name only when it helps the user recognise the service; still review any difference in procedure, eligibility or limits.
4. **Incomplete online extraction and image-based snapshot:** the online handbook outline omits parts of some tables and truncates some paragraphs. The 76-page local snapshot preserves the visible pages but is untagged and image-based. Use OCR and manual page/table checks rather than relying on either the outline or an ordinary PDF text loader.
5. **Image-heavy historical PDF:** the AY2024/2025 PDF has 78 pages but only about 1,700 extracted characters across the file; visual pages contain much more content. An ordinary PDF text loader would lose much of the source. OCR and manual table checks may be required if this file is used.
6. **Date ambiguity:** retrieval date, a site's copyright footer, and a search engine's crawl date are not policy effective dates.

## Approval and provenance fields

For each approved document/section, retain: source ID, title, original URL, edition, retrieval date, effective date if known, campus applicability, user category, section/page locator, local representation, content hash, approval status and reason, and public-redistribution status.

Use a frozen, reviewed source set for experiments. Apply this source-precedence rule: use the latest officially linked handbook as the default authority for edition-specific policy; use current official UTM Library webpages as reliable supplementary sources; and allow a newer applicable dated official notice to supersede the handbook only when that relationship is explicit and recorded. Treat naming differences separately from substantive differences. If eligibility, procedure, duration, charge or campus applicability still conflicts after applying this rule, hold the affected claim and use a limitation/redirect response. Do not claim the 2024/2025 edition remains current merely because a downloadable copy is available.

## Web sources and the course PDF checkpoint

Official webpages and an officially linked HTML5 flipbook can be knowledge sources for this project. The V1 system and final showcase do not require every approved source to exist as an offline PDF. HTML may be processed directly, while reviewed sections from a flipbook may be captured or extracted into a reproducible local knowledge snapshot. PDF is one possible source representation, not a measure of authority or recency.

For reproducible testing and a reliable showcase, preserve the approved text or page images, source URL, edition, retrieval date, locator and content hash in the local knowledge snapshot. This snapshot does not have to be a PDF and does not need to be publicly redistributed. A retrieval date records when content was actually checked; it does not need to match the final submission date unless the source is retrieved again.

The course PDF checkpoint is a separate preparation requirement for the Week 3 parsing activity. A browser-produced PDF should be labelled as a webpage or flipbook snapshot with its original title, URL, capture date and completeness check; it is not a publisher-issued PDF. The two reader exports obtained on 1 November 2026 are technically valid local PDF inputs. Confirm with the lecturer only if the exercise specifically requires publisher-provided downloads rather than reviewed snapshots. Do not count an online flipbook URL alone as an offline PDF.

Lab 1 and the current `Sources/` directory record eleven local PDFs: six FAQ webpage snapshots, one membership-page snapshot, one rules-page snapshot, the historical AY2024/2025 handbook, the current AY2026/2027 handbook snapshot and the FAQ 2025 compilation snapshot. These are local representations of fewer underlying official sources, not eleven independent authorities. The Week 3 numerical checkpoint can be met with two or three suitable current-domain snapshots; the current handbook, FAQ compilation and one focused webpage snapshot provide a practical mix for OCR, tagged-text and HTML-to-PDF parsing. The historical handbook should not be treated as current policy. The successive “at least 2” and “2–3” checkpoints are not cumulative requirements for 4–5 different files.

Reading a public page does not automatically permit redistributing its entire content in a public repository. The Lab 1 PDF snapshots currently remain local. Keep source files local unless redistribution is permitted; the public repository can retain source metadata and retrieval instructions instead.

## Relationship to Lab 2 and later implementation

The **V1 corpus** is not a separate Part A, Part B or Part C submission file. In Lab 2, Part A defines its scope, authority, provenance and Responsible AI requirements, while Part C represents it conceptually through K1 candidate sources, K2 source review and preparation, K3 approved knowledge, and ADR3's reviewed snapshot. The actual extraction, normalisation into JSON or Markdown records, chunking, indexing and retrieval implementation belong to later data-engineering and RAG work. Before formal evaluation, the approved subset will be frozen so that the assistant and keyword-search baseline use the same content.
